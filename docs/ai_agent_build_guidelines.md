# Research Data Command Center AI Agent Build Guidelines

Status: **master product guideline**

This document is the project-level guide for AI-assisted design and build work. It supersedes earlier product/menu guidance, while `docs/shared_data_contract.md` remains the stricter engineering contract for shared identifiers, storage boundaries, lineage, and schema discipline.

## Product Direction

Research Data Command Center is a researcher-facing platform for managing, observing, and analyzing AI research data workflows.

It connects:

```text
Datasets -> Training Runs -> Checkpoints -> Model Versions -> Evaluations -> Failures -> Next Dataset / Next Run
```

The product should feel like an internal research data platform for technical researchers, ML platform engineers, and data platform teams. It should not feel like a generic dashboard.

## Final Navigation

```text
Research Data Command Center
├── Home
├── Datasets
├── Runs
├── Models & Evaluations
├── Workspace
├── Docs
└── Settings
```

Rules:

- Dataset lineage belongs inside Datasets.
- Run lineage belongs inside Runs.
- Model lineage belongs inside Models & Evaluations.
- API and SDK documentation belongs under Docs, not as a top-level product pillar.

## Core Data Domains

The platform must support these 11 domains:

1. Dataset records
2. Dataset versions and lineage
3. Dataset quality and filtering results
4. Training run configs
5. Training run telemetry
6. Compute and system telemetry
7. Checkpoints and artifacts
8. Model versions and lineage
9. Evaluation cases and outputs
10. Evaluation scores and failure analysis
11. Researcher interaction metadata

## Data Source Labels

Agents must label every source:

- `PUBLIC_REAL`: real public large-size data where possible.
- `GENERATED_REAL`: real model, run, evaluation, quality, metadata, or lineage outputs generated by our own pipelines using public data or small models.
- `SYNTHETIC_REALISTIC`: realistic synthetic data used only when public or generated real data is unavailable, too expensive, or too slow.

Synthetic data must be documented and must obey realistic constraints. PII examples must use fake/test examples only.

## Technical Direction

- Frontend: React / Next.js
- Backend: FastAPI
- Processing: Python, Pandas/Polars, DuckDB
- Analytical storage: Parquet + DuckDB
- App metadata: Postgres
- Raw/artifact storage: local object-store-style folders for MVP
- Experiment tracking: MLflow-style logs, metrics, params, and artifacts
- Evaluation: custom eval runner first
- SDK: Python package wrapping FastAPI endpoints

## Build Phases

1. Planning and Alignment: confirm scope, architecture, navigation, agents, data rules, and demo story.
2. Data Foundation: shared layout, IDs, naming, source plans, and initial schemas for the 11 domains.
3. Backend Foundation: FastAPI structure, data access, route organization, errors, pagination/filtering, and tests.
4. Dataset Vertical Slice: ingestion, catalog, detail, quality, versions, lineage, usage, and SDK methods.
5. Runs Vertical Slice: configs, metrics, compute telemetry, active runs, run detail, checkpoints, lineage, and SDK methods.
6. Models & Evaluations Vertical Slice: registry, evals, comparisons, failures, regressions, lineage, and SDK methods.
7. End-to-End Research Loop: failure-to-dataset workflow, review queue, and full cross-domain lineage.
8. Docs, SDK, and Portfolio Polish: docs, examples, architecture diagram, demo script, screenshots, and resume framing.

## Coordination Rules

- All agents consume the shared contract before proposing implementation.
- New shared keys, tables, endpoints, or cross-agent lineage edges require an owner checkpoint.
- Every UI feature must be backed by an API endpoint.
- The SDK should mirror the most important researcher workflows.
- Build a realistic vertical slice before expanding breadth.
- Stop at checkpoints for confirmation before implementation.
